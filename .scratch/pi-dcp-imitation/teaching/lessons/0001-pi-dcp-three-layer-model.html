第 1 课 · pi-dcp 原理

pi-dcp 的三层心智模型

@pi-vault/pi-dcp（v0.5.0，MIT）是 pi 的一个上下文管理扩展。要解决的问题是：每个 MCP 工具调用都往上下文塞原始数据（一次 Playwright 快照 56 KB，一份日志 45 KB），而 pi 原生压缩只在 contextTokens > contextWindow − reserveTokens（reserve 默认 16 k）时才触发——对 1 M 窗口意味着用到 ~984 k 才压，太晚。R2 · compaction.md

pi-dcp 不替换 pi 的压缩管线，它骑在上面，用三件事管上下文。记住这三层，你就有了读它源码的地图。

三层机制

  • 硬 · 自动 ① 自动剪枝策略 (automatic pruning)
    dedup（去重重复的工具输出）+ purgeErrors（N 轮后清掉失败的旧工具输入）。静默、常开、不靠 agent——直接改消息。
    源：src/strategies/{deduplication,purge-errors,runner}.ts · R1 §5
  • 软 · nudge ② Nudge 提醒
    上下文 % 越过阈值（maxContextPercent 80 / minContextPercent 50）时，注入 <dcp-system-reminder> 提醒 agent：“你现在必须 compress”。靠 agent 响应，可被忽略。
    源：src/prompts/nudges.ts（CONTEXT_LIMIT_NUDGE / TURN_NUDGE / ITERATION_NUDGE）+ src/prompts/system.ts 经 before_agent_start 注入 · R1 §2–3
  • agent · 主动 ③ compress 工具
    agent 调 compress 工具，对一段消息做 range → summary block。由 agent 主动发起，不是 pi-dcp 自己跑。
    源：src/compress/{handler,state,search,protected-content}.ts + src/pipeline.ts（7 步）· R1 §4
关键洞察：pi-dcp 从不硬触发 compaction。
它在源码里没有 compact() / summarize() 调用。context 钩子只是 runPipeline → return {messages}（index.ts:462）；session_compact 是 pi 已经压缩之后的事后监听（index.ts:323，记 “compaction detected”）；连 dcp:compress 命令也只是发一条隐藏 follow-up 消息（commands/compress.ts:19–26）。所以“真正的压缩”只有两条路：① agent 听 nudge 去调 compress 工具；② pi 原生晚触发兜底。pi-dcp 不驱动，只骑在上面。

附带惊喜：nudgeForce（"soft" | "strong"）是死配置——声明 + 校验，但代码从不读它（src/config-schema.ts:91）。所以你把它设成 strong 也不会让 nudge 更强，nudge 永远是同一句。

检索练习：pi-dcp 的三层里，哪一层不靠 agent、自动硬剪枝？
先在脑子里答，再点开核对

① 自动剪枝策略（dedup / purgeErrors）。
另外两层都靠 agent：② nudge 只是注入提醒，压不压由 agent 决定；③ compress 工具得 agent 主动调。
这也正是“被动/晚”体验的根因——pi-dcp 没有任何一层会自己硬触发压缩。
